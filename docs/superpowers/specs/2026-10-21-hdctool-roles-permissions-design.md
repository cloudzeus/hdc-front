# HDCtool — Ρόλοι & δικαιώματα (drag & drop) και σύνδεση χρηστών με SoftOne

- **Ημερομηνία:** 2026-10-21
- **Repo υλοποίησης:** `cloudzeus/hdckolleris` (HDCtool: Next 15, Prisma 6/MySQL με `db push` στο boot, better-auth, shadcn, `@dnd-kit` ήδη εγκατεστημένο)
- **Κατάσταση:** σχέδιο προς έγκριση

## 1. Σκοπός

1. Ο διαχειριστής ορίζει **ελεύθερους ρόλους** (π.χ. «Αποθήκη», «Πωλήσεις eshop», «Κατάλογος», «Λογιστήριο»). Κάθε χρήστης μπορεί να έχει **πολλούς ρόλους** και παίρνει το άθροισμα των δικαιωμάτων τους.
2. Σε κάθε ρόλο δίνονται, με **drag & drop**:
   - πρόσβαση σε **σελίδες** ή **ολόκληρες ομάδες** του μενού·
   - πρόσβαση σε **λειτουργίες** (π.χ. ERP, διαγραφές, voucher, θυρίδες).
3. Ένας χρήστης του HDCtool **μπορεί προαιρετικά να συνδεθεί** με χρήστη του SoftOne (`USERS`). Με τη σύνδεση:
   - γίνεται **εισαγωγή** χρηστών από το SoftOne·
   - το **ενεργός/ανενεργός** του SoftOne ισχύει και στο HDCtool·
   - γίνεται **καταγραφή** του ποιος έκανε τι προς το SoftOne.

   **Η σύνδεση δεν είναι προϋπόθεση.** Χρήστες χωρίς λογαριασμό στο SoftOne χρησιμοποιούν κανονικά το HDCtool, με τους ρόλους τους:
   - δεν επηρεάζονται από τον συγχρονισμό·
   - δεν κλειδώνονται ποτέ από το SoftOne·
   - οι ενέργειές τους προς το SoftOne γίνονται με τον κοινό λογαριασμό του API και καταγράφονται στο HDCtool με το όνομά τους.

**Κριτήρια επιτυχίας:**
- Ένας EMPLOYEE με ρόλο «Αποθήκη» βλέπει στο μενού μόνο τις σελίδες του ρόλου του.
- Αν ανοίξει άλλη σελίδα με URL, βλέπει «Δεν έχετε πρόσβαση».
- Δεν μπορεί να εκτελέσει κρίσιμη λειτουργία που δεν του έχει δοθεί.
- Την ημέρα της ενεργοποίησης κανείς δεν χάνει πρόσβαση που έχει σήμερα (§6).

**Εκτός σκοπού:**
- το portal προμηθευτών `/sup` (μένει με `SUP_PORTAL_ROLES`)·
- τα server-to-server κλειδιά (`requireHdcAdmin`, ApiKey, cron)·
- τα eshop·
- το B2B portal·
- η εγγραφή χρηστών στο SoftOne (μόνο ανάγνωση `USERS`).

## 2. Σημερινή κατάσταση (origin/master, 2026-10-21)

- **Ρόλος χρήστη:** `User.role` είναι enum `UserRole` (USER, ADMIN, EMPLOYEE, MANAGER, CUSTOMER, SUPPLIER). Δεν υπάρχουν πίνακες ρόλων ή δικαιωμάτων.

- **Μενού:** στατικό, στο `src/components/admin/app-sidebar.tsx`. Έχει 10 ομάδες και 89 σελίδες, χωρίς δικαιώματα ανά σελίδα. Ομάδες:
  - `eshop`
  - `acs`
  - `catalog`
  - `softone`
  - `softone-tables`
  - `milwaukee`
  - `b2b`
  - `lockers`
  - `content`
  - `settings`
- **Έλεγχοι στον server:**
  - `requireStaffSession`, `getStaffSession`, `assertStaffAction` (περίπου 260 endpoints).
  - Περίπου 180 έλεγχοι `role === "ADMIN"`.
- **better-auth:** `cookieCache` 24h. Το `customSession` εκθέτει μόνο `id, name, email, image, createdAt, role`.
- **SoftOne:**
  - Ένας κοινός λογαριασμός: web account με `REFID 15`.
  - Το `getClientID(userId?)` αγνοεί το `userId`.
  - Μερικά routes κάνουν δικό τους login: `erp-logs/resubmit`, `mtrl-products/erp-update`, `erp-pricing-update`, `products/bulk-import-to-erp`, `scripts/specifications-generation` και τα `*/sync`.
- **Έλεγχος στο SoftOne (2026-10-21):**
  - Το `login` του web account επιστρέφει ως επιτρεπτό μόνο το `REFID 15`.
  - `authenticate` με άλλο `REFID` απαντά «invalid credentials» (-2).
  - `GetTable USERS` δουλεύει: 32 χρήστες, από τους οποίους μόνο 5 έχουν email.
- **Αρχείο καταγραφής:** δεν υπάρχει γενικό audit log.

## 3. Κατάλογος δικαιωμάτων (στον κώδικα)

### 3.1 Μία πηγή για μενού και κατάλογο

Τα δεδομένα του μενού μεταφέρονται από το `app-sidebar.tsx` στο `src/lib/rbac/nav-config.ts`: ομάδες, σελίδες, εικονίδια, badges. Από εκεί τα διαβάζουν:
- το μενού, όπως σήμερα·
- το `src/lib/rbac/catalog.ts`, που παράγει τα κλειδιά.

| Είδος | Κλειδί | Παράδειγμα |
|---|---|---|
| Ομάδα | `group:<id>` | `group:lockers` |
| Σελίδα | `page:<href>` | `page:/admin/eshop-orders` |
| Λειτουργία | `feature:<key>` | `feature:erp.write` |

**Κανόνες καταλόγου:**
- Μια **σελίδα** επιτρέπεται αν ο χρήστης έχει το `page:` κλειδί της ή το `group:` κλειδί της ομάδας της. Μια ομάδα καλύπτει και σελίδες που θα προστεθούν αργότερα σε αυτήν.
- **Υποσελίδες** (π.χ. `/admin/eshop-orders/[id]`) ανήκουν στη σελίδα με το μεγαλύτερο ταιριαστό πρόθεμα, με τον ίδιο κανόνα που χρησιμοποιεί σήμερα το `activeHref`.
- **Σελίδες εκτός μενού** δηλώνονται ρητά στο `nav-config.ts` ως `hidden`, με ομάδα. Παραδείγματα: `/admin/erp-jobs`, `/admin/milwaukee-jobs`, `/admin/_soft-reference`.
  - Ένα test ελέγχει ότι κάθε `src/app/admin/**/page.tsx` αντιστοιχεί σε κλειδί, ώστε καμία νέα σελίδα να μην ξεχνιέται.
- Το **`/admin/dashboard`** επιτρέπεται πάντα σε όλο το προσωπικό, ως σελίδα προσγείωσης. Τα ποσά σε αυτό ελέγχονται από το `feature:amounts.view`.
- Μια σελίδα ή ομάδα που **δεν έχει δοθεί σε κανέναν ρόλο** τη βλέπει μόνο ο ADMIN.

## 4. Δεδομένα (Prisma, μόνο προσθήκες)

```prisma
model AppRole {
  id          String              @id @default(cuid())
  name        String              @unique @db.VarChar(80)
  description String?             @db.VarChar(255)
  color       String?             @db.VarChar(16)
  isSystem    Boolean             @default(false)   // ο μεταβατικός ρόλος
  createdAt   DateTime            @default(now())
  updatedAt   DateTime            @updatedAt
  permissions AppRolePermission[]
  users       UserAppRole[]
  @@map("app_roles")
}

model AppRolePermission {
  roleId    String
  key       String   @db.VarChar(191)   // group:… | page:… | feature:…
  createdAt DateTime @default(now())
  role      AppRole  @relation(fields: [roleId], references: [id], onDelete: Cascade)
  @@id([roleId, key])
  @@map("app_role_permissions")
}

model UserAppRole {
  userId     String
  roleId     String
  assignedAt DateTime @default(now())
  assignedBy String?                    // email διαχειριστή
  user       User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  role       AppRole  @relation(fields: [roleId], references: [id], onDelete: Cascade)
  @@id([userId, roleId])
  @@index([roleId])
  @@map("user_app_roles")
}

model SoftOneUser {                      // αντίγραφο του SoftOne USERS
  s1Id        Int       @id              // USERS.USERS
  code        String    @db.VarChar(50)
  name        String    @db.VarChar(120)
  email       String?   @db.VarChar(191)
  mobile      String?   @db.VarChar(40)
  isActive    Boolean
  isWebUser   Boolean   @default(false)
  missingSince DateTime?                 // δεν επιστράφηκε στον τελευταίο συγχρονισμό
  syncedAt    DateTime
  @@map("softone_users")
}

model AuditLog {
  id          String   @id @default(cuid())
  at          DateTime @default(now())
  actorUserId String?
  actorEmail  String?  @db.VarChar(191)
  action      String   @db.VarChar(64)   // role.create, role.grant, role.revoke, user.role.assign, softone.link, softone.sync, softone.user.locked, softone.write …
  targetType  String?  @db.VarChar(32)
  targetId    String?  @db.VarChar(64)
  s1Refid     Int?                        // με ποιον χρήστη SoftOne έγινε η κλήση
  details     Json?
  @@index([at])
  @@index([actorUserId, at])
  @@index([action, at])
  @@map("audit_logs")
}
```

**Προσθήκες στο `User`:**
- `softoneUserId Int? @unique`, η σύνδεση με τον χρήστη `SoftOneUser.s1Id`·
- `lockedBySoftOne Boolean @default(false)`·
- οι σχέσεις `appRoles UserAppRole[]`.

Οι αλλαγές είναι μόνο προσθήκες, οπότε το `db push` στο boot τις περνά χωρίς κίνδυνο.

## 5. Υπολογισμός και επιβολή

### 5.1 Πυρήνας (`src/lib/rbac/`)

- **`getEffectivePermissions(user)`** επιστρέφει:
  - ADMIN → `ALL`·
  - MANAGER/EMPLOYEE → το σύνολο κλειδιών όλων των ρόλων τους·
  - οτιδήποτε άλλο → κενό.

  Cache ανά χρήστη στη μνήμη για 30″. Η cache καθαρίζει σε κάθε αλλαγή ρόλου ή ανάθεσης. Το HDCtool τρέχει σε ένα container.
- **`can(perms, key)`**: για σελίδα ελέγχει το `page:` κλειδί ή το `group:` της ομάδας της· για λειτουργία ακριβές κλειδί. Είναι καθαρή συνάρτηση και έχει tests.
- **`requirePermission(headers, key)`** (για API) επιστρέφει 403 `{ error, required: key }`.
- **`assertPermission(key)`** (για server actions) πετάει σφάλμα με ελληνικό μήνυμα.
- Τα δικαιώματα **δεν** μπαίνουν στο cookie. Έτσι μια αλλαγή ρόλου ισχύει μέσα σε περίπου 30″, χωρίς αποσύνδεση.

### 5.2 Φάση 1

1. **Μενού:**
   - Το `admin/layout.tsx` υπολογίζει τα δικαιώματα και περνά στο `AdminShell`/`AppSidebar` τη λίστα επιτρεπτών κλειδιών.
   - Το μενού κρύβει σελίδες και κενές ομάδες. Η αναζήτηση του μενού ψάχνει μόνο στις επιτρεπτές σελίδες.
2. **Σελίδες:**
   - Το `middleware.ts` περνά το pathname στο header `x-hdc-pathname`.
   - Το `admin/layout.tsx` αντιστοιχεί το pathname σε κλειδί (§3.1).
   - Αν δεν επιτρέπεται, εμφανίζεται η σελίδα «Δεν έχετε πρόσβαση», μέσα στο κέλυφος του admin. Δείχνει τους ρόλους του χρήστη και το κείμενο «ζητήστε από διαχειριστή» και έχει κουμπί για τον πίνακα ελέγχου.
3. **Λειτουργίες:** έλεγχοι `requirePermission`/`assertPermission` στα σημεία του πίνακα §3.2.
   - Οι υπάρχοντες έλεγχοι `role === "ADMIN"` **μένουν ως έχουν**. Μια λειτουργία που σήμερα είναι μόνο για ADMIN συνεχίζει να είναι μόνο για ADMIN.
4. **Κρυφά στοιχεία στη σελίδα:** κουμπιά για λειτουργίες χωρίς δικαίωμα δεν εμφανίζονται. Ο server τα αρνείται έτσι κι αλλιώς.

### 5.3 Φάση 2 (σταδιακά, μετά τη φάση 1)

- Το `requireStaffSession(headers, { permission })` αποκτά προαιρετικό κλειδί.
- Κάθε `src/app/api/**` που εξυπηρετεί μια σελίδα δηλώνει το `page:` ή `feature:` κλειδί της.
- Η δουλειά γίνεται ανά ομάδα του μενού, με ένα commit ανά ομάδα.
- Οι έλεγχοι `role === "ADMIN"` που αντιστοιχούν σε λειτουργία του καταλόγου μετατρέπονται σε `feature:` κλειδιά.
- Ένα script αναφοράς δείχνει πόσα endpoints δεν έχουν ακόμα κλειδί.

## 6. Μετάβαση χωρίς αλλαγή συμπεριφοράς

- **Αυτόματη δημιουργία μεταβατικού ρόλου:** με την πρώτη κλήση του `getEffectivePermissions`, αν ο `app_roles` είναι κενός, δημιουργείται μία φορά ο ρόλος **«Πλήρης πρόσβαση (μεταβατικός)»**.
  - Είναι `isSystem`.
  - Έχει όλα τα `group:*` και όλες τις λειτουργίες εκτός από το `feature:users.manage`, που σήμερα είναι μόνο για ADMIN.
  - Ανατίθεται σε όλους τους υπάρχοντες MANAGER/EMPLOYEE.
  - Γράφεται στο `AuditLog` ως `role.bootstrap`.
- Ο διαχειριστής φτιάχνει τους πραγματικούς ρόλους, μετακινεί τους χρήστες και διαγράφει τον μεταβατικό, με επιβεβαίωση.
- **Χρήστης προσωπικού χωρίς κανέναν ρόλο:** βλέπει μόνο τον πίνακα ελέγχου, με μήνυμα «Δεν σας έχει ανατεθεί ρόλος».
- **Νέος χρήστης:** η φόρμα «Νέος χρήστης» αποκτά πεδίο ρόλων. Για MANAGER/EMPLOYEE απαιτείται τουλάχιστον ένας ρόλος.
- **Προστασίες:**
  - Δεν γίνεται διαγραφή ρόλου που είναι ο μοναδικός ρόλος κάποιου χρήστη, χωρίς ρητή επιβεβαίωση. Η επιβεβαίωση δείχνει τους χρήστες που επηρεάζονται.
  - Ο ADMIN δεν επηρεάζεται ποτέ.

## 7. SoftOne

### 7.1 Συγχρονισμός χρηστών (μόνο ανάγνωση)

- `GetTable USERS` με πεδία `USERS, CODE, NAME, ISACTIVE, EMAIL, MOBILEPHONE, ISWEBUSER`.
- Η κλήση γίνεται μέσω του κεντρικού client: cp1253, ουρά, κοινό session.
- Το αποτέλεσμα γράφεται με upsert στο `softone_users`. Όσοι δεν επιστράφηκαν παίρνουν `missingSince`.
- **Πότε τρέχει:**
  - με κουμπί «Συγχρονισμός τώρα», με δικαίωμα `feature:users.manage`·
  - καθημερινά στις 06:30, ως job του υπάρχοντος `cron-manager` (μόνο σε production, όπως τα υπόλοιπα).
- Κάθε εκτέλεση γράφεται στο `AuditLog` ως `softone.sync`, με πλήθη: νέοι, αλλαγμένοι, ανενεργοί.

### 7.2 Σύνδεση και δημιουργία

Στη σελίδα `/admin/users` προστίθεται καρτέλα **«Χρήστες SoftOne»**: λίστα με κωδικό, όνομα, email, ενεργός και κατάσταση σύνδεσης.

**Προτάσεις σύνδεσης** (καθαρή συνάρτηση με tests):
- **Ισχυρή πρόταση:**
  - ίδιο email, χωρίς διάκριση πεζών/κεφαλαίων·
  - ή `CODE` του SoftOne ίσο με το τοπικό μέρος του email (`gkozyris` ↔ `gkozyris@…`).
- **Πιθανή πρόταση:** παρόμοιο ονοματεπώνυμο.
  - Σύγκριση χωρίς τόνους, πεζά, με μεταγραφή ελληνικών ↔ λατινικών.
  - Λαμβάνεται υπόψη και αντιστροφή ονόματος/επωνύμου.

**Ενέργειες:**
- **Σύνδεση** με ένα κλικ, ή επιλογή χρήστη HDCtool από λίστα.
- **Αποσύνδεση.**
- **Δημιουργία χρήστη HDCtool:** ανοίγει η υπάρχουσα φόρμα, συμπληρωμένη με όνομα, email αν υπάρχει και κινητό, μαζί με επιλογή ρόλων.
  - Το email είναι υποχρεωτικό για τη σύνδεση του χρήστη στο HDCtool.
- Ένας χρήστης SoftOne συνδέεται με το πολύ έναν χρήστη HDCtool (`@unique`).
- Η σύνδεση είναι **προαιρετική**. Οι χρήστες του HDCtool χωρίς σύνδεση εμφανίζονται ως «χωρίς SoftOne» και λειτουργούν κανονικά.
  - Η δημιουργία νέου χρήστη στο HDCtool **δεν** απαιτεί χρήστη SoftOne.
  - Η σύνδεση γίνεται και εκ των υστέρων, από όποια πλευρά: από την καρτέλα «Χρήστες SoftOne» ή από την επεξεργασία του χρήστη HDCtool, με πεδίο «Χρήστης SoftOne (προαιρετικό)».

Στη λίστα χρηστών του HDCtool προστίθεται στήλη/badge «SoftOne: <code>», ή «χωρίς σύνδεση».

### 7.3 Ενεργός/ανενεργός

Μετά από κάθε συγχρονισμό, **μόνο για τους συνδεδεμένους χρήστες**. Οι χρήστες χωρίς σύνδεση δεν αγγίζονται ποτέ.

- **Ανενεργός στο SoftOne** (`ISACTIVE=0` ή `missingSince`), όταν ο χρήστης δεν είναι ήδη κλειδωμένος:
  - `banned=true`, `banReason="Ανενεργός στο SoftOne (αυτόματος συγχρονισμός)"`, `lockedBySoftOne=true`·
  - διαγραφή των sessions του·
  - καταγραφή `softone.user.locked`.
- **Ξανά ενεργός** και `lockedBySoftOne=true`:
  - `banned=false`, `lockedBySoftOne=false`·
  - καταγραφή `softone.user.unlocked`.
  - Χειροκίνητο κλείδωμα (`lockedBySoftOne=false`) **δεν** αναιρείται ποτέ από τον συγχρονισμό.
- **ADMIN:** δεν κλειδώνεται ποτέ αυτόματα. Εμφανίζεται προειδοποίηση στη λίστα και καταγράφεται `softone.user.admin-inactive`.

### 7.4 Καταγραφή ενεργειών προς SoftOne

**Context χρήστη:**
- Τα `requireStaffSession`, `getStaffSession`, `assertStaffAction`, `requirePermission` και `assertPermission` αποθηκεύουν τον τρέχοντα χρήστη σε `AsyncLocalStorage` (`src/lib/rbac/actor-context.ts`): id, email, `softoneUserId`.
- Τα cron και τα jobs τρέχουν με actor `system:<job>`.

**Κεντρικό σημείο καταγραφής:**
- Οι κλήσεις εγγραφής (`setData`, `delData`, `calculate` με αποθήκευση, `eInvoice` και οι custom υπηρεσίες εγγραφής) γράφονται στο `AuditLog` ως `softone.write`. Καταγράφονται object, key, service, ο actor και το `s1Refid` που χρησιμοποιήθηκε.
- Ο κεντρικός `makeSoftOneRequest` περνά τα στοιχεία αυτά στον `logSoftOneWrite`.
- Τα routes που σήμερα κάνουν δικό τους login (§2) μεταφέρονται στον κεντρικό client στη φάση 1, ώστε να μην ξεφεύγει καμία εγγραφή.

**Κλήσεις με τον χρήστη του καθενός:**
- Μετά το `login`, ο client κρατά τη λίστα επιτρεπτών REFID (`objs`).
- Αν ο actor έχει `softoneUserId` που είναι στη λίστα:
  - η κλήση γίνεται με clientID εκείνου του REFID·
  - το clientID κρατιέται για όλη τη μέρα και ξανασυνδέεται μόνο στα -100/-101, όπως ο υπάρχων κανόνας.
- Αλλιώς η κλήση γίνεται με τον κοινό λογαριασμό (σήμερα `REFID 15`).
- Η σελίδα «Χρήστες SoftOne» δείχνει ποιοι χρήστες είναι «ενεργοποιημένοι στον web λογαριασμό».
- **Ενέργεια στο ERP (όχι κώδικα):** ο διαχειριστής του SoftOne προσθέτει τους χρήστες στον web λογαριασμό του API. Μέχρι τότε όλα δουλεύουν με τον κοινό λογαριασμό, με πλήρη καταγραφή στο HDCtool.

## 8. Σελίδα «Ρόλοι & δικαιώματα» (`/admin/roles`, ομάδα «Ρυθμίσεις»)

Δικαίωμα πρόσβασης: `feature:users.manage` (ο ADMIN το έχει πάντα).

### 8.1 Καρτέλα «Επεξεργαστής» (διάταξη Α)

**Αριστερή στήλη: Ρόλοι**
- Λίστα ρόλων με χρώμα και πλήθος χρηστών.
- Ενέργειες: νέος ρόλος, μετονομασία/χρώμα/περιγραφή, αντιγραφή, διαγραφή με επιβεβαίωση που δείχνει τους χρήστες που επηρεάζονται.
- Κάτω από τον επιλεγμένο ρόλο: οι χρήστες του ως chips με αρχικά και όνομα.
  - Προσθήκη χρήστη με σύρσιμο από το πάνελ «Χρήστες» (αναζήτηση, popover) ή με κουμπί «+».
  - Αφαίρεση με ✕.

**Μεσαία στήλη: «Διαθέσιμα»**
- Οι σελίδες ομαδοποιημένες όπως στο μενού, με αναζήτηση και σύμπτυξη.
- Η κεφαλίδα ομάδας σέρνεται ως ολόκληρη ομάδα.
- Ενότητα «Λειτουργίες» με εικονίδιο κεραυνού και σύντομη περιγραφή κάθε λειτουργίας.
- Ό,τι έχει ήδη ο ρόλος εμφανίζεται αχνό, με ένδειξη «✓».

**Δεξιά στήλη: «Έχει πρόσβαση»**
- Περιοχή απόθεσης με την ίδια ομαδοποίηση.
- Μια σελίδα που καλύπτεται από ομάδα φαίνεται ως «μέσω ομάδας» και δεν αφαιρείται ξεχωριστά.
- Αφαίρεση με σύρσιμο προς τα έξω ή με ✕.

**Αποθήκευση**
- Κάθε κίνηση αποθηκεύεται αμέσως (server action, optimistic UI).
- Εμφανίζεται toast «Προστέθηκε: Θυρίδες → Αποθήκη» με κουμπί **Αναίρεση** για 5″.
- Αν η αποθήκευση αποτύχει, η αλλαγή επιστρέφει πίσω και εμφανίζεται μήνυμα με «Δοκιμάστε ξανά».

### 8.2 Καρτέλα «Πίνακας»

- Ρόλοι (στήλες) × ομάδες/σελίδες/λειτουργίες (γραμμές) με checkboxes.
- Οι γραμμές ομάδων συμπτύσσονται. Στη στήλη της ομάδας εμφανίζεται «μερικώς» όταν μόνο κάποιες σελίδες της είναι επιλεγμένες.
- Είναι η εναλλακτική χωρίς σύρσιμο, πλήρως χρηστική από πληκτρολόγιο.

### 8.3 Καρτέλα «Ιστορικό»

- Το `AuditLog` φιλτραρισμένο σε `role.*`, `user.role.*`, `softone.*`.
- Φίλτρα: χρήστης, ενέργεια, ημερομηνία.

### 8.4 «Δες ως χρήστης»

- Επιλέγεις χρήστη και βλέπεις τους ρόλους του, το μενού όπως θα το δει και τις λειτουργίες του.
- Είναι μόνο προβολή. Δεν γίνεται πραγματική σύνδεση ως άλλος χρήστης.

### 8.5 UX και προσβασιμότητα (ui-ux-pro-max)

- `@dnd-kit/core` + `sortable` με `PointerSensor` (απόσταση ενεργοποίησης 6px), `KeyboardSensor` και `TouchSensor` (καθυστέρηση 150ms).
- `DragOverlay` με κάρτα που ακολουθεί τον δείκτη.
- Οι περιοχές απόθεσης φωτίζονται όταν δέχονται το στοιχείο, με χρώμα accent και διακεκομμένο περίγραμμα.
- Ανακοινώσεις για αναγνώστες οθόνης στα ελληνικά, μέσω `announcements` του dnd-kit.
- Περιοχές πατήματος τουλάχιστον 44px και κενό τουλάχιστον 8px ανάμεσα σε στοιχεία.
- Ορατό focus ring.
- Animation 150–200ms ease-out. Με `prefers-reduced-motion` το animation απενεργοποιείται.
- Κάτω από 1024px οι τρεις στήλες γίνονται καρτέλες «Ρόλοι · Διαθέσιμα · Πρόσβαση». Το σύρσιμο λειτουργεί με touch, και το «+» είναι πάντα διαθέσιμο.
- Τα στοιχεία του shadcn (Card, Badge, Tabs, Command για αναζήτηση, AlertDialog, sonner) χρησιμοποιούνται με τα υπάρχοντα tokens του HDCtool.
- Τυπογραφία με fluid rem tokens (κανόνας CLAUDE.md), χωρίς σταθερά px.
- Κενές καταστάσεις:
  - «Δημιουργήστε τον πρώτο ρόλο»·
  - «Σύρετε εδώ σελίδες ή ομάδες από τη λίστα Διαθέσιμα».

## 9. Σφάλματα και ακραίες περιπτώσεις

- **Ταυτόχρονη επεξεργασία:**
  - Οι προσθήκες είναι idempotent upsert στο `(roleId, key)`.
  - Οι αφαιρέσεις είναι idempotent delete.
  - Δεν απαιτείται κλείδωμα.
- **Κλειδί που αφαιρέθηκε από τον κώδικα** (σελίδα που καταργήθηκε):
  - αγνοείται στον υπολογισμό·
  - στη σελίδα ρόλων εμφανίζεται ως «παλιό δικαίωμα», με κουμπί καθαρισμού.
- **SoftOne μη διαθέσιμο κατά τον συγχρονισμό:**
  - δεν αλλάζει τίποτα (κανένα κλείδωμα)·
  - καταγραφή αποτυχίας και μήνυμα στη σελίδα.
  - **Ποτέ** δεν κλειδώνονται χρήστες επειδή ο πίνακας γύρισε κενός. Αν οι γραμμές είναι λιγότερες από το 50% της προηγούμενης φοράς, ο συγχρονισμός σταματά με προειδοποίηση.
- **Αφαίρεση δικαιώματος από χρήστη που βρίσκεται στη σελίδα:** στο επόμενο αίτημα, μέσα σε περίπου 30″, βλέπει «Δεν έχετε πρόσβαση».

## 10. Δοκιμές

- **Unit (vitest):**
  - `can`/`getEffectivePermissions`: ADMIN, πολλαπλοί ρόλοι, ομάδα → υποσελίδα, κρυφές σελίδες, παλιά κλειδιά, χωρίς ρόλο.
  - Αντιστοίχιση pathname → κλειδί.
  - Κάλυψη όλων των `page.tsx` (§3.1).
  - Μεταβατικός ρόλος: idempotent.
  - Προτάσεις σύνδεσης SoftOne: email, code, ελληνικά/λατινικά, αντιστροφή ονόματος.
  - Κανόνες κλειδώματος/ξεκλειδώματος, μαζί με την προστασία ADMIN και το κατώφλι 50%.
  - Επιλογή REFID ανά actor.
- **Integration:** τα server actions ρόλων γράφουν σωστά και καταγράφονται στο `AuditLog`. `requirePermission` → 403.
- **Browser (τοπικά, με τοπική βάση ή staging):**
  - Χρήστης με ρόλο «Αποθήκη»: μενού, απευθείας URL → άρνηση, κουμπί λειτουργίας κρυφό.
  - Drag & drop με ποντίκι και πληκτρολόγιο.
  - Αναίρεση.
  - Προβολή σε κινητό.
- **SoftOne:** συγχρονισμός `USERS` χωρίς εγγραφή στο SoftOne. Κανένα setData στις δοκιμές.

## 11. Παραδοτέα και σειρά

1. **Πυρήνας RBAC:** κατάλογος, μοντέλα, υπολογισμός, μεταβατικός ρόλος, `AuditLog`, tests.
2. **Φάση 1 επιβολής:** μενού, φύλαξη σελίδων, σελίδα άρνησης, έλεγχοι λειτουργιών §3.2.
3. **Σελίδα `/admin/roles`:** επεξεργαστής, πίνακας, ιστορικό, «Δες ως χρήστης».
4. **SoftOne:**
   - συγχρονισμός `USERS`·
   - καρτέλα «Χρήστες SoftOne»·
   - κλείδωμα/ξεκλείδωμα·
   - context χρήστη και καταγραφή εγγραφών·
   - μεταφορά των routes με δικό τους login·
   - REFID ανά χρήστη.
5. **Τεκμηρίωση:** `docs/rbac.md` στο HDCtool, με οδηγίες για νέα σελίδα ή νέα λειτουργία.
6. **Φάση 2:** σταδιακά, ανά ομάδα, με ξεχωριστό πλάνο.

**Κανόνες για το deploy:**
- Κάθε παραδοτέο γίνεται push μόνο με έγκριση.
- Τα βήματα 1–2 ενεργοποιούνται μαζί με τον μεταβατικό ρόλο, ώστε να μην αλλάξει η πρόσβαση κανενός.
